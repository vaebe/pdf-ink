# PDFInk 代码审查标准与流程

- **版本**：1.0（2026-09-20）
- **适用**：`src/**`、`scripts/**`、`index.html`、`vite.config.ts`、`package.json` 及仓库内文档
- **配套**：`docs/code-review-checklist.md`（可复制的速查清单）、`.github/pull_request_template.md`（提交入口）
- **定位**：本文是审查的**判据来源**。争议时以本文的条款为准；本文未覆盖的，按规定补齐后回写本文。

---

## 0. 为什么需要这份标准（现状诊断）

先明确一件事：**本项目的代码卫生是达标的，标准不该在那里重复劳动。**

2026-09-20 对 `src/**` 的实测扫描：

| 机械维度                                            | 实测 | 结论       |
| --------------------------------------------------- | ---- | ---------- |
| `any` / `@ts-ignore` / `lint-disable`               | 0 处 | 已达标     |
| 非空断言 `!.`                                       | 0 处 | 已达标     |
| `console.log/debug/warn`                            | 0 处 | 已达标     |
| `TODO` / `FIXME` / `HACK`                           | 0 处 | 已达标     |
| 裸吞异常                                            | 0 处 | 已达标     |
| `vp check`（格式 + Oxlint + typeAware + typeCheck） | 全绿 | 由工具强制 |

也就是说，**「参差不齐」不发生在这些维度，标准写成「检查有没有 any」对公司没有增量**。四轮真实审查（`docs/code-review-2026-09-20.md` 第一至三节/第七节/第八节）的缺陷分布才是依据：

| 缺陷类别                    | 轮次分布   | 典型案例                                                                                                                            |
| --------------------------- | ---------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| **异步竞态 / 过期结果写回** | 每轮都有   | P2-4 旧画布被新文档改写、P2-5 保存闸门晚了 `await` 一行                                                                             |
| **资源生命周期与释放**      | 第二、三轮 | I-2 失败打开泄漏 worker、P2-3 离屏不释放像素缓冲                                                                                    |
| **隐式契约被无意破坏**      | 每轮都有   | 居中溢出不可达、`rootMargin` 实际为 0、`clamp` 只约束一侧                                                                           |
| **生命周期/挂载语义误判**   | 第二轮     | `PdfViewer.vue:151` 的 `watch(documentId)` 被 `:key` 重挂载架空，永不可达                                                           |
| **验证不可复现**            | 结构性     | ~~54 项验收与 41 个探针脚本全部在 `/private/tmp/pdf-ink-fixtures/`，**不在版本控制内**~~ → 已迁入 `tests/acceptance/`（2026-09-20） |

由此得出三个结论，也是本文的组织原则：

1. **审查精力投在 `vp check` 管不到的地方** —— 运行时行为、生命周期、契约一致性。
2. **把隐式契约显式化** —— 本项目大量约定存活在注释、README 与个人记忆里，审查无法据此判定「有没有被破坏」。故设第 5 节《不可回退契约登记表》。
3. **没有可复现的验证就没有审查** —— 这一点是当前最大的系统性缺口（见第 8 节整改第 1 项）。

## 1. 严重度分级

### 1.1 四级定义

| 级别        | 定义                                                                                 | 本项目的判定示例                                                                                                                      |
| ----------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| **P0 阻塞** | 数据损坏或丢失、安全漏洞、**隐私承诺被破坏**、不可回退契约被破坏且无补偿             | 改写原始文件；引入任何远端请求／CDN 引用（违反「全程本地处理」）；导出坐标契约错误导致签名写错位置；引入 XSS 的 `v-html`／`innerHTML` |
| **P1 严重** | 功能性错误（用户可感知的错误行为）、资源泄漏、跨会话状态污染、**可稳定复现**的竞态   | I-2 失败打开泄漏 PDF.js worker；P2-4 切换文档后缩略图空白且不自愈；I-3 确认框孤立残留使按钮变成静默 no-op                             |
| **P2 一般** | 边界条件下的行为偏差、触达路径较窄的竞态、交互不完整、可维护性显著下降、**缺少验证** | P2-1 极端缩放下左侧不可达；P2-2 贴边放置导出被裁剪；M-1 极端缩放下缩放方向反转；新增可验收行为未补 `data-testid`                      |
| **P3 建议** | 命名、注释、可读性、可选结构改进；不影响行为的整理                                   | 卷起 `PdfViewer.vue:151` 的不可达 `watch`；抽公共比较函数                                                                             |

与早期文档的对应关系（便于阅读历史报告）：`Critical → P0`、`Important → P1/P2`、`Minor → P2/P3`。**新一轮审查统一用 P0—P3**，不再使用 Critical/Important/Minor。

### 1.2 分级必须遵守的三条规则

1. **按「影响面 × 触发概率」定级，不按「改动行数」定级。** 一行早写晚写的差别（P2-5 的 `isSaving`）可以是 P2；而 200 行重命名通常是 P3。
2. **禁止降级的三种理由**（历史上出现过，明确禁止）：
   - ❌「现有验收没有覆盖到，所以不算缺陷」—— 验收未覆盖恰恰是**必须补断言**的信号（见 4.1 R5）。
   - ❌「看着没问题／我理解代码是这样」—— 运行时行为结论必须有运行时证据，静态观感不构成证据。
   - ❌「这个条件现实中很少出现」—— 触发条件罕见只影响 P1/P2 的取舍，不能降成 P3 而静默放过。
3. **竞赛类缺陷的定级看触发路径**：走主流程即可触发（如「切换文档」）→ P1；需要极端视口、异常输入、后台标签页等条件 → P2。**但无论 P1 还是 P2，都必须修或登记**（见 1.3）。

### 1.3 门禁规则：什么级别必须修

| 级别 | 处理要求                                                                                           |
| ---- | -------------------------------------------------------------------------------------------------- |
| P0   | **必须修复后合并**，无例外，不接受「下轮再修」                                                     |
| P1   | **必须修复后合并**；若确需延后，须由合并者书面同意并在 PR 中登记为带 owner 的 issue                |
| P2   | **必须修复，或登记为 issue**。登记时必须写明触发条件与影响面，并注明「已知未修」。**不得静默通过** |
| P3   | 不阻塞合并，采纳与否由作者决定；未采纳不必说明理由                                                 |

审查结论用语（与历史上的 `REQUEST_CHANGES` 保持一致）：

- `APPROVE` —— 无 P0/P1/P2 未决项
- `APPROVE_WITH_COMMENTS` —— 仅有 P3，作者可自行决定
- `REQUEST_CHANGES` —— 存在未修复的 P0/P1/P2

## 2. 审查流程

### 2.1 角色

| 角色       | 职责                                                                                    |
| ---------- | --------------------------------------------------------------------------------------- |
| **作者**   | 写代码；**提交前自检并运行全部门禁**（第 3 节）；修复审查意见；为每条修复提供可复现证据 |
| **评审者** | 按第 4 节清单与第 5 节契约表逐项核对；产出结构化审查记录；判定严重度与结论              |
| **合并者** | 核对门禁结果与审查结论；确认 P0/P1 已修、P2 已修或已登记；执行合并                      |

**约束**：作者不得自审。本项目当前为小团队，若某次变更确无第二人可用，以「**隔轮复审**」替代 —— 作者在下一个工作时段以评审者身份重新走一遍清单，并在审查记录中注明「自审（隔轮）」，同时**不得豁免任何机器门禁**。

### 2.2 六个阶段

```
① 事前登记 ──→ ② 提交前自检 ──→ ③ 机器门禁 ──→ ④ 人工审查 ──→ ⑤ 修复与复验 ──→ ⑥ 记录归档与合并
   (作者)          (作者)           (作者/CI)        (评审者)         (作者)            (评审者/合并者)
```

| 阶段             | 输入         | 动作                                                                                          | 产出                                        |
| ---------------- | ------------ | --------------------------------------------------------------------------------------------- | ------------------------------------------- |
| ① 事前登记       | 需求/设计    | 判断本次变更是否触及**不可回退契约**（第 5 节）。触及则先说明：契约怎么变、谁补偿、补哪条断言 | 一句结论：「触及契约 N 条」或「未触及契约」 |
| ② 提交前自检     | 工作区       | 逐项过 `docs/code-review-checklist.md` 的「提交前」栏                                         | PR 描述中的自检勾选                         |
| ③ 机器门禁       | 暂存内容     | 跑第 3 节五道门禁，记录命令与原始输出                                                         | PR 中的验证证据段                           |
| ④ 人工审查       | PR + diff    | 按第 4 节清单；对每处可疑点**必须实际验证**，不得只凭阅读下结论                               | 结构化审查记录（2.4）                       |
| ⑤ 修复与复验     | 审查记录     | 逐条修复 P0/P1/P2；**每条修复附可复现证据**；修复后重跑门禁                                   | 更新后的审查记录（追加「处理结果」）        |
| ⑥ 记录归档与合并 | 全部门禁通过 | 合并者核对；审查记录归档到 `docs/`                                                            | 合并提交 + 归档的审查报告                   |

**④ 的关键要求 —— 没有证据的结论不成立。** 本项目历史上最有价值的发现都来自「实际跑一遍」：`rootMargin` 失效是探针逐页打印坐标才发现的；P2-4 的症状要靠注入回调延迟才能确定性复现。**评审者提出 P1/P2 时必须附触发方式**（命令、输入、观察值）；无法触发时，只能提出 P2 以下的「可疑项」，并明确标注「未实证」。

### 2.3 变更规模与轮次

- **建议单次变更 ≤ 400 行有效代码**（不含生成物、lock 文件、快照）。超过时拆分为可独立验证的多次提交。
- **一个 PR 只做一件事**。功能实现与样式重构、功能实现与无关清理不得混在一次提交里 —— 本项目已出现过「跑格式化误改他人正在编辑的文档」这类混入问题（见第 6 节 A-4）。
- **轮次上限**：同一问题连续三轮审查仍未收敛，停止继续往返，改为线下对齐根本原因，再回到流程。
- **每轮审查必须给出完整意见**（一次性列全），不得挤牙膏式分批提。这是对评审者的硬要求。

### 2.4 审查记录格式

审查记录是流程的正式产出，必须结构化并可归档。文件命名与位置：`docs/code-review-<YYYY-MM-DD>.md`（同一主题多轮则追加章节，不新建文件）。最小字段：

```markdown
## 审查记录：<主题>（<日期>，第 N 轮）

- **基准**：以 HEAD（或指定提交）为基准，覆盖未提交改动及新增文件
- **审查者**：<角色/人>
- **结论**：APPROVE | APPROVE_WITH_COMMENTS | REQUEST_CHANGES
- **门禁结果**：<逐条命令 + 实测结果，含通过/失败的数量>

### 问题清单

| 编号 | 级别 | 位置            | 症状           | 触发条件（实测）   | 建议修法 |
| ---- | ---- | --------------- | -------------- | ------------------ | -------- |
| P1-1 | P1   | `src/x.vue:120` | 用户可感知的…… | 步骤 1→2→3，实测…… | ……       |

### 处理结果（修复轮追加）

| 编号 | 处理 | 证据                                                  |
| ---- | ---- | ----------------------------------------------------- |
| P1-1 | 已修 | 探针 `p1-verify.mjs` 断言 3 条，修复前转红/修复后通过 |

### 本轮未处理

- <编号>：<原因 + 谁在什么时候处理>
```

`docs/code-review-2026-09-20.md` 是这一格式的实例（第一至三节为首轮，第七、八节为后续两轮），可直接参照。

## 3. 机器门禁

### 3.1 五道门禁

| #   | 门禁               | 命令                                     | 覆盖                                                                      | 通过标准                           |
| --- | ------------------ | ---------------------------------------- | ------------------------------------------------------------------------- | ---------------------------------- |
| 1   | 格式 / Lint / 类型 | `vp check <改动路径>`                    | Oxfmt + Oxlint（含 `typeAware`/`typeCheck`）                              | 0 error / 0 warning / 0 type error |
| 2   | 构建               | `vp run build`                           | 资源同步 + `vue-tsc -b` + 生产构建                                        | 构建成功，无 TS 错误               |
| 3   | 数值契约           | `vp test --project geometry`             | 坐标与导出契约（23 个用例：原 86 项数值断言、PDF 工具检查与加密导出拒绝） | 全部通过                           |
| 4   | 空白与差异卫生     | `git diff --check`                       | 行尾空白、文件末尾多余空行、CRLF                                          | 无输出                             |
| 5   | 浏览器验收         | `vp test --project acceptance`（见 3.2） | 端到端行为（1 个连续用例、59 项断言）                                     | 全部通过，连续两轮结论一致         |

新增/修改可验收行为时，门禁 5 必须**同步新增断言**（见 4.1 R5），否则该门禁不构成对本次变更的覆盖。

### 3.2 本项目执行门禁的六条注意事项（踩过的坑，务必遵守）

1. **`vp check` 按改动范围执行，不要跑全仓 `vp check --fix`。** 全仓会连带改写 `public/pdfjs/wasm/*.js`（PDF.js 随包生成物）与既有方案文档，产生大量无关 diff，属无关清理。
2. **`git diff --check` 不覆盖未跟踪文件。** 新增文件须用文本文件扫描（行尾空白 / 末尾多余空行 / CRLF / 缺结尾换行）单独确认，否则新文件里的空白问题会漏过门禁 4。
3. **pre-commit 钩子会改动你的暂存内容。** `core.hooksPath = .vite-hooks/_`，钩子内容是 `vp staged`，对暂存文件跑 `vp check --fix` 并**回写**。提交后必须确认 `git diff HEAD` 为空且 `git stash list` 为空 —— 否则说明回写没进提交。
4. **门禁 5 执行期间，不要写项目目录下的任何文件。** `vp dev` 对项目根目录下任何文件的写入都会触发**整页重载**，冲掉验收脚本在页面里打的补丁，表现为「某个断言莫名失败 + 30 秒点击超时」，极易误判为产品缺陷（写 `/tmp` 或 `.workbuddy/` 不受影响）。
5. **门禁 3 必须用 Vite+/pnpm 托管的 Node（24.x）。** 用系统 Node 22 会报 `Promise.try is not a function`。pdfjs-dist 在 Node 侧必须导入 `pdfjs-dist/legacy/build/pdf.mjs`。
6. **提交时路径集合要自洽。** `pnpm-lock.yaml` 必须随 `package.json`；`scripts/` 是 `postinstall`/`dev`/`build` 的前置依赖，只提交 `package.json` 而漏掉 `scripts/` 会让全新克隆的 `pnpm install` 直接失败。

### 3.3 豁免规则

- 仅 **P3 级、且不影响构建/运行** 的门禁失败可申请豁免，须在 PR 中写明**文件名、失败原因、为何不修**。
- **P0/P1/P2 相关文件的任何门禁失败一律不可豁免。**
- 全仓 `vp check` 的存量非合规文件（`public/favicon.svg` 缺结尾换行等）**不属于本次变更的失败**，但必须在 PR 中列明「已知存量、未处理、原因」，以免「全绿」变成依赖路径参数的伪结论。

## 4. 审查清单

### 4.1 本项目高风险类目（R1—R6）

这六类的判据来自本项目四轮审查的实际缺陷分布，**是本清单的核心**，权重高于 4.2 的通用类目。

#### R1 异步竞态与过期结果写回

**为什么**：本项目缺陷密度最高的类别，每轮审查都有。根因集中在「`await` 之后世界已经变了」。

**怎么查**：对每个 `await`，问三个问题 —— ① 返回后写回的共享状态，是否仍属于同一个「代次」？② 闸门（能否再次进入）是否在**进入第一个 `await` 之前**就已置位？③ 闸门复位是否也被验证？

**判据**：

- 检查所有跨 `await` 的写回点是否核对了身份（本项目已用的手段：`requestId`/`latestRequest`、`renderToken`、`currentSession !== session.value`、DOM 节点身份、`handedOver`）。
- 检查被取消的任务是否会写入缓存/标记（**过期任务写缓存是隐形的永久损伤**）。
- **不能只跑一遍正常流程就下结论**：这类竞态在 happy path 下常常跑不出来（实测：观察器首次回调只比 DOM 更新晚 2—5ms，stale 分支已被身份检查挡住）。确定性复现要求在页面内替换 `IntersectionObserver`／`toBlob`，**只给回调投递加固定延迟**（不改回调内容），再断言状态量。

**真实反例**：

- P2-5：`isSaving` 在 `cropToInk()`（内含 `await toBlob()`）**之后**才置位 → 窗口期内可重复保存，点「取消」关掉窗口后首个任务仍继续落库。
- P2-4：`watch(documentId)` 的 flush 是 `pre`，触发时 DOM 还没更新、手里还是旧画布，用新文档编号往旧画布上画，完成后把新页面标记为已渲染 → 新画布永久跳过渲染。

#### R2 资源生命周期与释放

**为什么**：PDF 渲染是重量级资源（像素缓冲、文本层、worker），放大倍数与 DPR 会成倍放大占用。

**怎么查**：① 释放的东西是「重」的还是「轻」的？② 有没有只增不减的计数器？

**判据**：

- **只释放可重建的重资源，保留还原所需的轻资源**。本项目已确立：离屏释放 `canvas` 像素缓冲与文本层，**保留 `viewport` 与 links** —— 签名层要靠 `viewport` 把实例还原到页面上，丢掉它会让页面一离屏签名 DOM 整体消失，**静默打破跨页实例计数的验收断言**。
- 度量方式用「**已渲染过的数量 vs 仍持有缓冲的数量**」，而不是绝对值。旧实现下二者同步增长，修复后为 `26 → 3`（O(1)）。
- 清理路径要覆盖**所有出口**：加载失败、中间步骤失败、请求过期、交接后兜底。本项目用「所有权标记 + 单一 `finally`」收拢。

**真实反例**：I-2 读取页几何失败时异常直达 `openFile` 的 catch，`loadingTask` 从未经过任何一处 `destroy()` → 每次失败打开泄漏 1 个 worker 且后续成功打开不回收。

**反面的过度修复**：只合闸门不复位（弹窗永久停在「保存中…」且无法取消）。见 4.1 R5。

#### R3 契约一致性（坐标 / 布局 / 样式）

**为什么**：同一语义存在两条路径时，只修一侧就会出现「预览正常、导出异常」这类割裂症状。

**判据**：

- **同一语义只有一条实现路径**。已确立的例子：初次放置（`placeAt`）与后续拖动（`applyMatrix`）都必须调用 `clampMatrixToViewBox` —— 预览层不裁剪越界部分，导出却受页面可见区域限制，只约束一侧就会「预览完整、导出缺一角」。
- **样式：同一个属性不得同时出现静态工具类与条件工具类**（如 `class="border-line" :class="x ? 'border-accent' : ''"`）。优先级相同，胜负由样式表顺序决定而非类名书写顺序 → 激活态/放置模式会**静默失效**。条件类一律用三元表达式只输出一组。
- **改动第 5 节登记表中的任一条**，按 5.2 的额外要求处理。

#### R4 生命周期与挂载语义

**为什么**：本项目已出现「写了但永远不会执行」的代码，这类问题静态阅读极难发现。

**判据**：

- **`watch` / `onMounted` 是否真的会执行**？反例：`PdfViewer.vue:151` 的 `watch(documentId, ...)` 与父组件 `App.vue:346` 的 `:key="documentId"` 冲突 —— 组件在 `documentId` 变化时被重挂载，该 watcher **永不可达**（约 5 行死代码，且会误导后续维护者以为这里处理了切换逻辑）。
- **`IntersectionObserver` 的 `root` / `rootMargin` 是否真的生效**？`root: null` 时 `rootMargin` 只扩大视口矩形，交叉矩形仍会被中间滚动容器的可视区裁剪 → **900px 预渲染余量实际为 0**。必须把 `root` 显式指向滚动容器。
- **不要按结构类推**。同一写法在不同组件上结论可能相反：`PdfPage.vue` 上 `root: null` 导致余量失效，而缩略图的 240px 余量**实测有效**。改前必须用量具重新测（`thumb-margin-probe.mjs`），不得推导。

#### R5 验证与验收钩子

**为什么**：审查的效力上限由验证的可用性决定。本项目「验收脚本不在仓库内」是当前最大的系统性缺口。

**判据**：

- **新增可验收行为必须补 `data-testid`**（或 `data-*` 钩子），否则脚本会以「找不到元素」失败 —— 更糟的情况是**静默通过**。定位一律走钩子，**不要绑视觉类名**。
- **断言不得恒真**。典型反例：用 `canvas.width > 0` 判断「是否已渲染」—— 未渲染的 `<canvas>` 默认就是 300×150，该判定恒真，会在完全空白的界面上通过。本项目写法：`canvas.style.width` 有值且不是 300×150。
- **每条断言应有区分力对照**：证明它能在旧实现下转红。做法是把「逐片段回退根因」做成可复跑的对照工具（本项目为 `p3-control.mjs`，支持 `apply`/`restore`/`status`）。**没有对照的断言只证明「当前恰好通过」，不证明它守住了什么。**
- **过度修复要反向断言**：只合闸门不复位这类过修，失败模式是「永久卡住」。故闸门类断言必须正反成对：窗口期内拒绝重复提交 **且** 成功后闸门复位、弹窗可重开（A14-5～A14-7）。

#### R6 隐私与本地处理边界

**为什么**：`README.md` 对外承诺「PDF 与签名均在浏览器内处理，不上传任何服务器」，这是产品级承诺，破坏即为 P0。

**判据**：

- **不得引入任何远端请求**：新增依赖、字体、CDN、分析脚本、远程 PDF.js 资源，都要确认构建产物中无远端引用。PDF.js 的 worker/CMap/标准字体/WASM/ICC 必须由本站点 `public/pdfjs` 提供。
- **原始文件永不改写**：导出始终另存为 `原名-signed.pdf`；`File` 对象只读，任何「原地保存」的思路都是 P0。
- **确认交互一律走应用内 dialog**（`requestConfirm`），不使用原生 `window.confirm`/`alert` —— 原生弹窗既破坏体验，也会让浏览器验收脚本无法交互（B6 专门断言全程未出现原生弹窗）。

### 4.2 通用类目

| 类目         | 审查要点                                                                                                                                                                                                                                    |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **正确性**   | 边界条件（空文档、单页、损坏文件、极端视口、0/90/180/270 旋转 + 非零 CropBox）；错误路径有提示且不破坏既有会话；状态机不存在不可达/死代码分支                                                                                               |

### 5.2 改动契约的额外要求

任何触及上表的变更，必须在**同一个 PR 内**完成三件事，缺一不可：

1. **更新本表**：契约本身怎么变、为什么变。
2. **补/改断言**：第 5.1 节「守它的验证」列里，凡受影响的断言必须同步调整；新契约必须有新断言。
3. **提供区分力对照**：证明新断言能在旧实现下转红（方法见 4.1 R5）。

**契约变更 + 无断言 = 直接 P1**，无论改动看起来多小。

## 6. 本项目历史缺陷模式速查

五轮审查提炼出的七个反复出现的模式。**看到相似形状就提高警惕**，这七条在历史上贡献了绝大多数 P1/P2。

| 模式                         | 形状                                                                              | 历史案例                                                                                                                                             |
| ---------------------------- | --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A-1 「晚一行」**           | 闸门/标记放在了第一个 `await` 之后                                                | P2-5 的 `isSaving`；`cropToInk()` 里的 `await toBlob()` 就是那个窗口                                                                                 |
| **A-2 「旧节点写新数据」**   | 组件已换、引用已旧，但标识符已更新 → 写到了被移除的节点上，并把新节点标记为已完成 | P2-4：`watch(documentId)` 在 DOM 更新前拿到旧画布                                                                                                    |
| **A-3 「只约束一侧」**       | 同一语义有两条路径，只改了一条                                                    | P2-2：拖动有 `clamp`、初次放置没有                                                                                                                   |
| **A-4 「越界纠正」**         | 修 A 的过程中改动了不属于本变更范围的产出物                                       | 跑格式化时改写了并行工作流正在写的文档；「修」存量非合规文件                                                                                         |
| **A-5 「恒真断言」**         | 断言的判据在缺陷态下也成立，于是永远通过                                          | `canvas.width > 0`（默认 300×150）；`rootMargin` 写了但没生效                                                                                        |
| **A-6 「焦点掉到 body」**    | 点击不可聚焦内容后焦点落到 `document.body`，组件上的键盘处理再也收不到事件        | ConfirmDialog 点击正文后 Esc 失效；修复引入的副作用是 Shift+Tab 越出弹窗                                                                             |
| **A-7 「静态观感代替实测」** | 按框架/标准行为的常识推导运行时结论，不去实际跑一遍                               | 以为 `instanceof EncryptedPDFError` 可用（打包后原型丢失，恒为 false）；以为 Tab 循环会因缺 tabindex 而出错（Chrome 用点击位置作起点，实测照样通过） |

**A-4 的处理约定**：确认文件是否属于本次变更（`git show HEAD:<file>` 看是否本就如此、`git status` 看是否本就在改）。不属于则**不动它**，在报告中列明即可 —— 「全绿」不能靠悄悄扩大格式化范围获得。
