## 核对方式

验收过程同时使用三条互相独立的证据链，不用同一份代码自证：

| 环节     | 工具                                                     | 与产品的独立性                                       |
| -------- | -------------------------------------------------------- | ---------------------------------------------------- |
| 界面操作 | Playwright + Chromium 151（真实鼠标/指针事件、真实下载） | 真实浏览器，非模拟                                   |
| PDF 解析 | pypdf 6.19.0                                             | 与 pdf-lib / PDF.js 无关                             |
| PDF 渲染 | PDFium（pypdfium2）                                      | Chromium 的 PDF 引擎，与应用使用的 PDF.js 是不同实现 |

`A5-*.png` 与 `A5-*-pdfium-*.png` 是同一页的两侧证据：前者是应用预览截图，后者是用 PDFium 渲染导出的 PDF。
两组图应当完全一致；不一致即说明导出与预览脱节。

界面共有三处确认（切换文件时「放弃未导出编辑」、打开已签名文档时「签名会失效」、
删除签名模板），全部由页面内的 `[data-testid=confirm-dialog]` 呈现。验收脚本直接驱动该 DOM 弹窗
（读取 `confirm-title` / `confirm-message` / `confirm-details` / 按钮文案 / 初始焦点，
再点击指定按钮或按 `Esc`），并断言命中弹窗的标题与按钮文案，
避免取消路径因为命中了另一个确认框而假通过。

脚本其余定位同样走测试钩子：`toolbar`、`file-name`、`page-input`、`zoom-level`、
`signature-library`、`library-item(-pick/-name/-preview)`、`signature-pad-dialog(-canvas)`、
`pad-name-input`、`pad-error`、`banner` + `data-tone`、`pdf-scroller`、
`placement(-handle/-frame/-delete)`、`thumb-item` / `thumb-canvas`。
签名卡的激活态用 `data-active` 判断，不读类名。

脚本同时注册 `page.on("dialog")` 记录原生弹窗——改造后触发次数必须为 0（B6）。
这一条是必要的：脚本原先正是靠该钩子自动接受原生弹窗，改造后钩子不再触发，
若不改成驱动 DOM 并补上这条断言，确认框会被**静默跳过**而所有断言依旧「通过」。

**几何数据之外，还要验证「点得到」**：A9-4 / A9-5 用 `elementFromPoint` 在链接矩形内取样
5 个点，要求全部命中 `<a>` 且不在文本层内；再真实点击一次，断言打开了指向目标 URL 的标签页。
这类断言是必要的——透明的文本层 `<span>` 曾经压在链接层之上，吞掉全部指针事件，
而当时所有几何与导出断言**全绿**：链接注解确实还在 PDF 里，只是页面上点不动。
A9-5 的导航由 `context.route` 精确 stub，因此不产生外发流量；
A12-1 在统计外发请求时按**完整 URL**（而非整个域名）排除这一条，其余一律照旧严格判定。

**几何与命中之外，还要验证「够得到」与「放得下」**：A13 段对应第二轮审查的 3 项 P2，
它们同样属于「构建、类型、其余断言全绿也照样坏」的类别：

- **A13-1 布局可达性**：横向溢出时测量「`scrollLeft = 0` 时页面左边缘相对滚动原点的偏移」。
  该值为负即表示落进 `scrollLeft` 最小值 0 之外的区域——**滚不到，也放不了签名**。
  修复前该值为 −488px（300% 缩放，1280px 视口）。
- **A13-2 / A13-3 贴边放置**：贴着页面左边缘 6px、下边缘 6px 各放一次，
  断言实例矩形完整落在页面矩形内且**边缘被平移收边到 0 附近**；再导出用 pypdf 核对图片包围盒
  与页面可见区域的四边余量都不为负。预览层不裁剪越界部分，导出却受页面可见区域限制，
  只断言其中一侧就等于没测。
- **A13-4 / A13-5 / A13-6 离屏资源**：逐页浏览后统计两件事——画布后备缓冲（`canvas.width × height × 4`）
  与文本层节点数。断言**离屏页面两者都归零**，且「渲染过的页面数」远大于「仍持有缓冲的页面数」
  （旧实现下两者会同步增长）。A13-5 反向断言预渲染余量确实生效（折叠线以下的相邻页已提前渲染），
  否则「离屏即释放」会把滚动变成白页。旧实现下这些页面会一直占住约 190MB（DPR 2、文字密集样本）。
  这条用的是 `heavy-text-40p.pdf`：`book-100p.pdf` 每页只有 53 个字符，文本层泄漏只剩个位数节点，
  看不出实现差异；该样本每页约 3300 字符，41 页共约 1900 个文本节点，泄漏量才是真实量级。

**再进一步，还要验证「切换后仍画得出来」与「异步窗口里按键不重入」**：A14 段对应第三轮审查的
2 项 P2，都属于**正常操作下偶发、静态检查与其余断言全绿也照样坏**的异步竞态：

- **A14-1 / A14-2 切换文档后的缩略图**：切换后逐项采样面板内的 `canvas`，断言
  ①每个可视项都已绘制（采样像素不透明）、②没有任何画布停留在默认 `300×150`
  （未渲染过的 `<canvas>` 默认就是这个尺寸，只看 `width > 0` 会恒真）。
  A14-2 把面板滚到底，验证**新入视野的项**同样已绘制——这正是旧实现露馅的地方：
  缓存里写着「这页渲染过了」，新画布便永久跳过渲染。
- **A14-3 / A14-4 把竞态变成确定性复现**：直接按「打开 A → 打开 B」**复现不出来**——
  观察器的首次回调实践中只比 DOM 更新晚几毫秒，`getPage()` 还没来得及返回，
  stale 分支就已经被会话身份检查挡住了。脚本因此在页面内替换 `IntersectionObserver`，
  给命中缩略图的回调**投递**加 400ms 延迟（只延迟投递、不改回调内容），让 stale 渲染有机会跑完。
  A14-3 用 `MutationObserver` 盯着切换前那批画布的 `width/height` 属性写入，断言
  **改写 0 次**（并报告其中有多少次发生在已从 DOM 移除的节点上）。
  同一扰动下旧实现稳定 40 个画布被改写 80 次、全部 detached，8 个可视项全部空白且不自愈。
- **A14-5 / A14-6 / A14-7 保存签名的闸门**：在页面内给 `toBlob` 的回调加固定延迟，
  制造一个确定可点的「保存中」窗口。A14-5 断言窗口期内保存按钮 `disabled`、文案为「保存中…」、
  且点「取消」不会关闭弹窗；A14-6 断言窗口期内重复点击保存，签名库**只新增 1 项**；
  A14-7 是反向对照——保存成功后闸门必须复位，重开弹窗按钮不能停在「保存中…」、
  「取消」要能正常关闭（只合闸门不复位会把弹窗永久锁死，这一条专门防这种过度修复）。

## 复现方式

验收脚本**已纳入版本控制**：见 `tests/acceptance/`（脚本、探针、夹具）与 `tests/acceptance/README.md`
（前置条件、环境变量、运行方式）。本文件只保留某次运行的**结论留档**（截图、导出样本、报告）。

它需要以下外部工具：

- `playwright-core` + Chromium（Playwright 浏览器缓存中已有的 `chromium-1234`）
- Python 3.13 隔离环境：`pypdf`、`pypdfium2`、`pillow`

运行方式：

```bash
# 1) 生成合成样本（不含任何真实文档）
pnpm fixtures:make

# 2) 启动应用后执行验收（端口固定 5199，脚本默认指向它）
vp dev --port 5199

# 3) 单独核对某个 PDF
python tests/acceptance/python/pdf_probe.py <pdf>            # 页面几何、图片变换矩阵、注解、文字
python tests/acceptance/python/render_pdfium.py <pdf> <outdir>   # 用 PDFium 逐页渲染

# 4) Tailwind 迁移轮新增的样式核对
node tw-check.mjs    # 迁移前 style.css 的 55 项声明值 vs 真实浏览器计算样式
node tw-visual.mjs   # 签名库 / 编辑层 / 确认弹窗，浅色 + 深色各一遍
node dialog-dark.mjs # 重新生成 B2-dialog-signed-pdf-dark.png（验收脚本只跑浅色）

# 5) 审查修复轮新增的独立验证
node fix-verify.mjs  # 6 条断言：画布尺寸 / 链接命中与点击 / 切换态 hover
node p2-verify.mjs   # 15 条断言：布局可达性 / 贴边放置 / 离屏资源，含逐条区分力对照
node p3-verify.mjs   # 13 条断言：切换文档后的缩略图（含推迟投递的竞态复现）/ 保存签名闸门
node p3-control.mjs apply   # 反向对照：逐片段回退根因，跑 p3-verify 应转红；用完 restore 还原
node thumb-margin-probe.mjs # 附带核查：缩略图观察器的 240px 余量是否生效
```

`fix-verify.mjs` / `p2-verify.mjs` / `p3-verify.mjs` 与 `acceptance.mjs` 是相互独立的证据链：后三者除了
断言正确行为，还额外断言**「换一种测法就会得出相反结论」**，用来证明每条断言确实能区分新旧实现，
而不是恰好通过：

- 画布尺寸：验收视口下 `getBoundingClientRect` 折算 514–518，而布局折算恒为 524，
  差值正是入场动画那 2% 缩放。
- 布局可达性：`p2-verify.mjs` 在运行时注入 `min-width: 0` 复现修复前的行为，
  左边缘立刻变成 −488px（不可达）；不注入时恒为 +16px。
- 贴边放置：报告「若按点击中心直接摆放则应为 −118.2px / −23.2px」——这两个数本身就是越界值。
- 离屏资源：报告「渲染过的页面数」与「仍持有缓冲的页面数」，旧实现下二者同步增长（14 → 14），
  现在是 14 → 3；A13-5 反向断言预渲染余量生效（若余量带失效，该值会是 0）。
- 缩略图切换：`p3-verify.mjs` 注入 400ms 回调投递延迟。旧实现下 40 个旧画布被改写 80 次、
  全部 detached，8 个可视项全空白；新实现改写 0 次、空白 0 项。
  `p3-control.mjs` 把这条做成可复跑的对照：`apply` 回退根因后同一探针按预期转红，`restore` 还原。
- 保存闸门：报告窗口期内的按钮 `disabled` 与文案、点取消后弹窗是否仍在、库内新增项数。
  旧实现为 `disabled=false` / 弹窗被关掉 / 新增 2 项同名签名；新实现为 `true` / 弹窗保留 / 1 项。

> **运行验收期间不要改动项目目录下的任何文件。**
> `vp dev` 对项目根目录下任何文件的写入都会触发**整页重载**——包括 `docs/*.md`、根 `README.md`
> 这类不在模块图里的文件（实测确认；只有 `.workbuddy/` 因是点目录而被忽略）。
> 重载会冲掉 A2-2 给 `IDBObjectStore.prototype.put` 打的补丁，使「模拟存储失败」变成真的写入成功，
> 脚本随后以 30 秒点击超时崩溃。A2-2 现在会打印「用例期间整页重载 N 次」，
> 出现非 0 即可直接判定为调试期干扰，而不是产品缺陷。

合成样本：`plain.pdf`（2 页含文字）、`rotations.pdf`（0/90/180/270 + 非零 CropBox + 混合尺寸）、
`text-links.pdf`（可选文字 + 外链注解）、`book-100p.pdf`（100 页）、
`heavy-text-40p.pdf`（40 页 × 约 3300 字符，由 `make-heavy-text.mjs` 生成）、
`dot-40p.pdf`（40 页极轻量，由 `make-dot.mjs` 生成；A14 用它当切换目标，确保竞态窗口内
页面加载足够快，从而把问题收窄到缩略图观察器本身）、
`sig-field-empty.pdf`、`sig-field-signed.pdf`（数字签名字段）、`broken.pdf`（损坏文件）。
